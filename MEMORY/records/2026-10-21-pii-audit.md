## What Changed

Every response that returns unmasked NIK, NPWP, or bank account through
`listEmployees` or `getEmployee` now writes an `employee.pii.unmasked` audit
row inside the same transaction as the read. Previously only exports were
audited, so an HR insider holding `employee.pii.unmask` could read every
national ID on the list and detail screens with no trace.

## Why

Closes the High gap in `docs/PLAN/17` §9 and the Open abuse case (e) in
`docs/SECURITY/02` §8: "HR unmasks everyone's national ID in bulk" — the trail
had to show it. Implements `docs/PLAN/12` Phase 2 DoD ("unmasking recorded in
the audit log") and `docs/PLAN/00` §3.2 P5.

## How

The audit call sits inside the domain functions the route handlers call, not
in the handlers themselves, so no path can return unmasked PII without
leaving the row. `listEmployees` and `getEmployee` now take an
`ActorContext` (they previously took none on the read path); the two route
handlers pass `{ actorUserId: ctx.userId, ip, userAgent, correlationId }`.

Granularity: one row per read, not per employee. A list of 200 employees
unmasked is one row listing 200 employee ids — the row answers "who bulk
unmasked the whole list" without writing 200 rows. The row records
`before: null`, `after: { employeeIds, fields }`, actor, IP, user agent, and
correlation id. `fields` is the constant `['nationalId', 'taxId',
'bankAccount']` — the fields masking actually distinguishes. Phone, email,
and fullName are omitted because they are returned identically with and
without the permission, so they cannot distinguish an unmasked read and
auditing them would fire on every masked read too.

No PII value reaches the row — only ids and field names (hard rule 9).

## Decisions Made

| Decision | Rationale | ADR |
|---|---|---|
| One audit row per read, with all revealed employee ids in `after.employeeIds` | A list of 200 employees unmasked is one action by one actor; 200 rows would bury the actor-level fact and inflate the audit table for no extra answer | — |
| Audit inside the domain function, not the route handler | Route handlers stay thin; a handler that forgets cannot bypass the trail | — |
| `fields` lists only the three masked identifiers | Phone, email, and fullName are returned identically masked or not, so including them would make every masked list read write a row — noise, and it would dilute the meaning of the action | — |
| Unmasking is NOT opt-in per request (the task card's step-1 option was not taken) | The brief scoped this task to auditing; making `?unmask=1` opt-in changes the frontend contract and was not in scope. Holders of the permission still unmask by default, but now every such read is traceable | — |

## What Did Not Work

- The first version of the audit block passed `actorUserId: undefined` and
  relied on the caller not needing to identify the actor. That defeats the
  entire point of the row, and the type check caught it; the fix threads
  `ActorContext` through both functions.
- The commit was not created in this session. The working tree carries the
  changes uncommitted; per hard rule 17 they must be staged by explicit path
  (`packages/core/src/employee/employees.ts`, the two route files, the test,
  the docs, `TASKS/`, `MEMORY/`) with a `P2-08:` subject.

## Follow-Ups

- Consider the task card's step-1 option (unmask as an explicit per-request
  choice) as a separate task if product wants "chose to reveal" semantics;
  the audit row already supports either behaviour.

## What to Watch

- A future route returning unmasked PII through a different domain function
  (e.g. a new detail endpoint) must write the same row; there is no
  structural test asserting every `canUnmask` call site is audited. The
  signal would be an unmasked read that leaves no `employee.pii.unmasked`
  row for its actor.
